# Decisions log

One entry per decision, newest at the bottom. Each records the options that were on the table
with their pros and cons, who decided, when, and what it changed in the plan. Append; never
rewrite history — supersede with a new entry that links back.

Status values: **decided** · **open** · **superseded by D-nnn**.

---

## D-000 · Implementation stack — native SwiftUI
**Status:** decided · Shane · 2026-09-02

Options considered:
- **Native SwiftUI** — *pro:* peak platform polish; first-class Live Activities, HealthKit,
  Watch, widgets; no JS runtime. *con:* zero code reuse from the web (`src/lib` is ~12k lines of
  pure TS); either reimplement UI-state logic in Swift and move the rest server-side, or fork
  the coach; needs a Mac or macOS CI for every build; two languages to keep in sync.
- **React Native + Expo** — *pro:* reuses `src/lib` directly (coach tools, analytics engine,
  tracker model, recurrence), EAS builds from Linux, TypeScript across every session. *con:* not
  pixel-native; charts and drag libraries are third-party; Expo SDK churn; Live Activities still
  need a Swift widget extension.
- **Capacitor wrap of the web app** — *pro:* cheapest, one codebase. *con:* still the web app in
  a WKWebView — the keyboard, viewport and gesture problems mostly persist; least improvement.

**Decision:** native SwiftUI. Shane has a Mac. The reuse gap is closed by moving the four
browser-resident logic blocks server-side (see D-008) rather than by porting them.

## D-001 · Repository — monorepo, `ios/` directory
**Status:** decided · Claude (delegated by Shane) · 2026-09-02

- **Monorepo `ios/`** — *pro:* API shapes, NDJSON wire protocol, DB row types, coach tool
  schemas and design tokens change often and must land with the client that depends on them;
  one PR for coupled changes; one master doc; one CI; the existing multi-session harness
  (worktrees, claims, babysitter, supervisor report, deploy-verify) applies unchanged; public
  repo → free macOS runners. *con:* Node and Xcode in one tree; `npm ci` wasted for iOS-only
  worktrees (`--no-install`); a macOS CI job that must early-exit on non-iOS changes.
- **Separate `apex-training-ios`** — *pro:* Xcode-only tree, its own CI. *con:* the contract
  (API, DB types, tokens) has to be vendored and pinned to a web SHA and drifts silently; every
  coupled change is two PRs with ordering constraints; a second harness or none.

**Decision:** monorepo. `.xcodeproj` is git-ignored and generated by XcodeGen so parallel
worktrees never conflict on `project.pbxproj`.

## D-002 · Distribution — TestFlight first, App Store later
**Status:** decided · Shane · 2026-09-02

- **TestFlight first, App Store later** — *pro:* no App Review for internal testers; ship
  early; App Store work (privacy labels, account deletion, BYO-key review-proofing) becomes W13.
  *con:* 90-day build expiry forces a release cadence.
- **TestFlight only, indefinitely** — simplest; invite-only stays invite-only.
- **App Store from v1** — public listing from the start; puts review risk on the critical path.

**Decision:** TestFlight first. Apple Developer Program membership is required either way.

## D-003 · Offline — read cache + tracker write queue
**Status:** decided · Shane · 2026-09-02

- **Read cache + tracker write queue** — *pro:* covers the gym-without-signal case; moderate
  cost decided up front. *con:* a queue is stateful code that must be tested hard.
- **Read cache only** — cheap, but a tracker session still needs signal.
- **Online-only** — simplest; unusable without signal.
- **Full offline-first** — best experience; a sync engine is its own project.

**Decision:** read cache (GRDB, stale-while-revalidate) plus a per-session FIFO write queue for
tracker operations. See architecture.md §6–7.

## D-004 · Minimum iOS version — 17.0
**Status:** decided · Claude · 2026-09-02
Observation, mature Swift Charts, `NavigationStack` typed paths, `#Preview`,
`ASWebAuthenticationSession` are all 17.0. Nothing the app needs is 18-only (the new `Tab` API

## D-005 · Project generation — XcodeGen, `.xcodeproj` git-ignored
**Status:** decided · Claude · 2026-09-02
- **XcodeGen** — one `project.yml`, `brew install xcodegen`, no manifest toolchain on CI; the
  project file becomes a derived artifact, so parallel worktrees never conflict.
- **Checked-in `.xcodeproj`** — zero tooling, but `project.pbxproj` merge conflicts are the
  most common iOS monorepo failure with several sessions in flight.
- **Tuist** — more power than needed; a plugin/cache system to learn.

## D-006 · State management — MVVM on Observation, not TCA
**Status:** decided · Claude · 2026-09-02
After D-008 little reducer logic remains on the client, which is precisely where TCA pays off.
`@Observable @MainActor` view models with injected `ApexClient` and `Clock` protocols are
testable enough; the genuinely stateful pieces (write queue, chat session) are actors in
`ApexCore` with their own tests. TCA would add macros, compile time and a dependency graph a
solo owner plus AI sessions must keep current.

## D-007 · Local store — GRDB, not SwiftData
**Status:** decided · Claude · 2026-09-02
The cache is JSON blobs keyed by kind plus a durable ordered write queue: that wants explicit
SQL transactions, ordered reads and `ValueObservation`, not an object graph. SwiftData on iOS 17
has background-context and migration pain and cannot run in the Linux test target. GRDB's SQLite
file is also inspectable from `xcrun simctl` when debugging.

## D-008 · Where shared logic lives — server-side, behind the existing API
**Status:** decided · Claude · 2026-09-02

- **Move behind `/api/*`** — *pro:* `api/_lib/mcp/data.ts` already runs recurrence expansion,
  alias resolution, PR detection, period stats and block progress server-side for the MCP tools;
  the coach executors, tracker bootstrap and analytics engine are pure TS that already runs in
  Node; the `evals/` suite keeps validating one coach for both clients; fixes the documented
  "client-declared `triggered_by`" hole. *con:* ~1.5k lines of backend work across five PRs
  before the matching Swift screens; `api/chat.ts` import graph grows.
- **Reimplement in Swift** — *pro:* no backend churn. *con:* a permanently forked coach and
  analytics engine; ~4k lines with subtle rules (alias-widened history, superset re-lettering,
  RRULE edge cases) maintained twice.

**Decision:** server-side. Rule: **Swift never reimplements anything that has a `__tests__`
directory under `src/lib/`.** Swift owns UI state only (tracker edits and shadow-commit, chat
queue semantics, repeat chips, occurrence-id helper, formatting).

## D-021 · Swift package layout — two packages, and the generated row types live in `ApexAuth`
**Status:** decided · W1 session · 2026-09-03
architecture.md §1 implied five sibling packages. **Decision:** `ApexCore` alone, plus one
`ApexKit` package exposing `ApexAuth`, `ApexPersistence`, `ApexUI` and `ApexFeatures` as four
library products.

Why `ApexCore` stays separate is a hard constraint, not taste: `swift test --package-path
ios/Packages/ApexCore` must build the *whole* package on Linux, so one Apple-only target in it
ends the Linux gate. Why the rest are one package: every worktree resolves the graph from
scratch after `xcodegen generate`, and one package resolves supabase-swift and GRDB once
instead of four times with four manifests to keep in version step. The boundaries that matter
are still enforced, by target dependency edges inside the manifest.

The generated `DatabaseTypes.swift` moved from `ApexCore` to `ApexAuth` in the same change.
It compiles only with supabase-swift's `AnyJSON` (its one non-Foundation symbol, 69 uses),
which lives in the unexported `Helpers` module — so it is `import Supabase` or nothing, and
supabase-swift declares no Linux platform and pulls in `swift-syntax`. The generated enum is
`internal`, so a module of its own could not re-export it either. `ApexAuth` already owns the
Supabase client, which makes `internal` the right visibility. The emit is unchanged, so
`scripts/db-types.sh --check` still diffs clean; only `OUT_SWIFT` moved.

Considered and rejected: (a) `ApexCore` depends on supabase-swift — turns a zero-dependency,
offline, seconds-long Linux gate into a network-bound multi-minute one and breaks
architecture.md rule 2; (b) post-process the emit to strip `AnyJSON` — every future schema
change then carries a transform CI must reproduce byte-for-byte forever.

Enforced by a new `scripts/ci-guards.sh` block that greps `ApexCore/Sources` for Apple-only
and SDK imports: a Linux-runnable guard for a Linux-only property, so every run catches it
rather than only the one job that would notice.

## D-022 · Build configuration — xcconfig → Info.plist → `Bundle.main`
**Status:** decided · W1 session · 2026-09-03
Three configurations (`Debug`, `Local`, `Release`), each with an xcconfig supplying
`APEX_API_BASE`, `SUPABASE_URL` and `SUPABASE_ANON_KEY`. They reach Swift through Info.plist
keys read by `AppConfig`, so a built `.ipa` can be inspected to see what it points at.

`Local` is fully self-sufficient from values already committed in `.env.agent`; production
values live in `ios/Config/Secrets.xcconfig`, git-ignored, with an `.example` alongside. The
app traps at launch while the placeholder is unreplaced, and `AppConfig.assertSafe()` traps if
a **simulator** build points anywhere but `127.0.0.1` — the harness's "never point a local
build at production Supabase" rule, made mechanical instead of remembered.

Considered and rejected: user-defined settings inline in `project.yml` (nowhere to put a value
that must not be committed); `GENERATE_INFOPLIST_FILE` + `INFOPLIST_KEY_*` (only works for keys
Xcode knows); a generated `Config.swift` (forces a rebuild to switch, invisible in a built app).

Gotcha worth keeping: `//` starts a comment in xcconfig, so a URL written literally truncates
to `https:` with no error. URLs are written `http:$(SLASH)$(SLASH)host` with `SLASH = /`.

## D-023 · Two `src/lib` modules are ported to Swift despite having tests
**Status:** decided · W2 session · 2026-09-04
D-008 says Swift never reimplements anything with a `__tests__` dir under `src/lib/`. Two
exceptions, both wire-format parsing that cannot run server-side because it happens before a
request exists: `OccurrenceID` (`src/lib/schedule/occurrence.ts` — the `${baseId}__${date}`
split every schedule join keys off) and `AuthLinkError` (`src/lib/auth/linkError.ts` — GoTrue's
refusal fragment on an invite or recovery link, read from the URL that opened the app).

Parity is enforced the same way the rule would have been: the vitest vectors are copied verbatim
into `OccurrenceIDTests` / `DeepLinkTests` and run on Linux. A change to either TS module that
alters behaviour must change its test, and the copied Swift test then fails.

Considered and rejected: an endpoint that parses ids and fragments for the client (a network
round-trip to split a string, and the auth fragment arrives with no session to call it with).

Also recorded here from W2: month chips (22pt) cannot host a 44pt completion control, so U7 is
met through the day sheet's rows — one tap from any month cell — rather than a control on the
chip itself.
