## Approach

### Threshold, from the data
Measured 2026-11-08 over every tracked session in Shane's account (the only
account read: through his own MCP connector, `list_sessions` against
`get_schedule`'s planned minutes, 2026-07-01 to 2026-11-08). 112 sessions;
66 finished in the tracker (COROS imports and quick-completes, whose start
equals their finish, excluded).

| | ratio to plan | length |
|---|---|---|
| Longest normal session | 2.31× (a 30-min stretch, 69 min) | 1.57 h (an 80-min Weights B, 94 min) |
| Shortest runaway | 7.03× (a 29-min stretch, 2026-09-11) | 3.40 h |
| The other three runaways | 31×, 45×, 975× | 42 h, 22 h, 471 h |

The three runaways in the 2026-11-08 report are the 471 h, 22 h (1,339 min)
and 42 h (2,495 min) rows; the data held a fourth, the 3.40 h stretch. Every
rule from 3× to 7× separates the two groups. **4×** sits at the geometric
middle of the ratio gap (√(2.31 × 7.03) ≈ 4.0). The absolute floor separates
nothing in this data (4× alone flags the same four). It guards plans that
are short or wrong (a 2-minute "White Pine Adventure" is in the schedule). It
is **2 hours**, not the brief's 3: above the longest normal session with
26 minutes to spare, and a stretch forgotten for 2.5 h would slip under a
3-hour floor (5× its plan) while the shortest runaway cleared it by 24
minutes. A false prompt costs the athlete one tap; a missed runaway costs a
wrong number until someone repairs it.

### The rule and the suggestion
`runawayFinish.ts` is pure: `isRunaway(elapsedSeconds, plannedMinutes)`,
`suggestFinish({ startedAtMs, nowMs, plannedMinutes, lastLoggedMs })`,
`detectRunaway(clock)` (the two together, or null) and
`formatRunawayLength(seconds)` (`3 h 24 min`, `20 d 4 h`), plus
`latestLoggedAt(rows)` for the server. The vectors live in one JSON file both
suites read, the D-059 pattern, so the Swift port (D-061, M2) cannot drift.

### Server
`buildBootstrap` returns `lastLoggedAt` from the rows it already loads (no new
query). The `finish` window's lower bound becomes the earlier of a week ago
and the session's `started_at`: a finish inside the session's own span is its
real end, which `edit-times` already accepts. The only requests that change
from 400 to 200 are finishes between the session's start and a week ago;
before both still answers `timestamp-out-of-window`, inside the week but
before the start still answers "precedes", and the existing tests stand
unchanged. Side effect, intended: an offline iOS finish flushed more than a
week late now keeps its real time instead of being stripped to now.

### Web
`requestFinish(force, score, finishAt)` gains a third gate between the
unlogged-sets confirm and the score step: `needs-finish-time`, carrying the
elapsed seconds, the planned seconds and the suggested instant. `finishAt`
is `undefined` (not asked), `null` ("It ran …": no `finishedAt`) or an ISO
instant. The hook stamps the last local set or cardio edit of the sitting.
`FinishTimePrompt` is a bar in the confirm-bar family with a
`datetime-local` field (min = start, max = now) and three actions: Keep going,
It ran …, Finish at ….

### iOS (M2)
`TrackerModel.Gate` gains `.needsFinishTime`; `requestFinish` takes the
choice and threads the chosen instant into `FinishPayload.finishedAt`, the
summary, `markCachedFinished`, `activity.end` and `HealthWorkoutDraft`.
`FinishTimeCard` mirrors `ScoreCard` with a compact `DatePicker`.

No migration, no new endpoint, no new dependency, no `TECHSTACK.md` row.

## Decisions
- 2026-11-08 · Threshold 4× and 2 h, not the brief's 4× and 3 h (Approach).
- 2026-11-08 · No plan, no prompt. "Far past its plan" needs a plan, and the
  athlete who logs without one is Article I's floor; a new tap there raises
  it.
- 2026-11-08 · The suggestion counts set and cardio rows only, not notes or
  reorders: the brief's "last logged set", and the rows that carry a
  `updated_at` the server already stamps.
- 2026-11-08 · No idle-gap condition (last set long before Finish). It would
  spare a genuine long session that logs sets to the end, but that session
  is already past 4× its plan, the prompt's default is then within minutes
  of now, and either action costs the same one tap.
- 2026-11-08 · The prompt sits after the unlogged-sets confirm and before the
  score step, so a For Time score defaults to the corrected length.
- 2026-11-08 · "It ran …" sends no `finishedAt` on the web (byte-identical to
  today's finish); iOS keeps stamping now, as its queue always has.
- 2026-11-08 · The window is relaxed only for `finish`, and only back to the
  session's own start. `start` keeps its week.
- 2026-11-08 · `lastLoggedAt` is when the last set or cardio row was saved
  (`updated_at`), not when it was first logged: a swap relabel, a provider
  import or a late iOS flush moves it too (reviewer finding). The hint says
  "when your last set was saved", which is true either way; a true logged-at
  needs a column and a migration, out of scope for a default the athlete sees
  and can change.
- 2026-11-08 · Plans are almost never missing: the builder defaults one per
  type (`TYPE_DURATION`: weights 60, stretching 20, outdoor-climbing 240), so
  the threshold usually runs against a default the athlete did not pick. A
  default outdoor climb prompts only past 16 h, which is the intended
  restraint, not a gap.
- 2026-11-08 · Finish tapped again while the prompt is up re-detects and opens
  a fresh prompt (the web keys it on the detection), so a set logged meanwhile
  becomes the default and the field never disagrees with the action.
- 2026-11-08 · A finish that fails after the athlete answered (unsaved edits,
  no signal) keeps the answer: the next Finish goes out with it. A score step
  left open across the threshold still re-asks; no wrong data, too rare to
  carry the extra state.
- 2026-11-08 · The prompt's "It ran …" and its upper bound follow the
  tracker's live clock, so a prompt left open shows the real length.
- 2026-11-08 · iOS `isoTimestamp` rounds to the millisecond (M2 reviewer,
  critical): truncation sent a finish clamped to the start a millisecond
  before it, which the server refuses. D-061 records it.

## Learned
- Whole-second fixtures hid a 1 ms truncation in a shared iOS helper
  (`CompletionRows.isoTimestamp`). For half of all real starts, it would have
  sent a finish clamped to the start before the start, so the server would have
  refused it or recorded the whole runaway. Test data takes the production wire
  shape (PostgREST's milliseconds and `+00:00`), not round numbers.
- The reviewer found that bug and one other; every gate was green at the time.
  Running a reviewer per milestone (here, two) paid for itself on M2.
- One vector file read by both suites made the Swift port a translation, not a
  re-derivation. A threshold moved on one side fails the other suite.
- Measuring before choosing moved the floor from the brief's 3 h to 2 h. The
  ratio does the separating; the floor only guards bad or default plans.
- An old wire bound (the 7-day `finish` window), combined with the iOS queue's
  strip-and-retry, would have silently recorded the very runaway this feature
  stops. Read the wire contract end to end before a UI feature leans on it.
- The fleet babysitter skips a PR that conflicts and does not look at it again
  in the same run after the conflict is pushed away. Start it again once the
  conflict is resolved.

## Next brief
**Sessions started and never finished.** This feature makes Finish honest
about a session left running; it does nothing for the ones nobody ever
finishes. The 2026-11-08 measurement found 15 in Shane's history alone
(`list_sessions` rows with `finishedAt` null, the oldest started 2026-07-02:
stretches, two Weights A, a Weights B, a climbing day). Each is a runaway
waiting to happen and, until finished or cancelled, an open session the
schedule and the Live Activity may treat as current.

- *Goal:* an athlete with a session left open from an earlier day can close
  it truthfully in one decision, at the moment they next meet it, with no
  nagging in between (Article V: no streak guilt, no manufactured urgency).
- *Measure first:* how the web schedule, the iOS schedule (D-043's running
  indicator) and the Live Activity treat a session open for days; whether a
  second Start on another day of the same series reuses or orphans it; how
  many athletes beyond Shane have one (count only, through a read-only
  aggregate Shane approves, or his account alone).
- *Likely shape, to be decided in the spec:* when the tracker or the event
  sheet opens a session started on an earlier day and never finished, offer
  Finish (with this feature's prompt, which already defaults to the last
  saved set) or Discard, once. Nothing changes without the athlete
  (Article VII).
- *Owns (likely):* the tracker open path on both clients; no server change
  unless the measurement shows one. Spec under
  `docs/specs/abandoned-sessions/`.
